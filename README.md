# Honeycomb SDK

Honeycomb API client, generated from the OpenAPI spec.

The API allows programmatic management of many resources within Honeycomb.

Learn more about Honeycomb API at [docs.honeycomb.io](https://docs.honeycomb.io).

This is an unofficial SDK for the Honeycomb public API, generated by Muhammad Waqar with [`@voxgig/sdkgen`](https://github.com/voxgig/sdkgen). It is not affiliated with, endorsed by, or sponsored by the upstream API provider.

> TypeScript, Python, Golang SDKs, a CLI with an interactive REPL, and an MCP server for AI agents — all generated from one OpenAPI spec by [@voxgig/sdkgen](https://github.com/voxgig/sdkgen).

> **Features:** `test` — opt-in,

## About Honeycomb API

**Status:** generated on 2026-10-10 from Honeycomb's public OpenAPI spec (`https://docs.honeycomb.io/api/openapi-public.yaml`) with `@voxgig/sdkgen` 4.34.5. The offline test suites pass in TypeScript, Python and Go. On the same day, the TypeScript and Python SDKs, the CLI and the MCP server were checked against the live API (see the live check in [DX-REPORT.md](DX-REPORT.md#live-check)).

**Two kinds of key.** Honeycomb uses configuration keys for the `/1/` endpoints, sent in the `X-Honeycomb-Team` header, which is the client default. The `/2/` endpoints (`ApiKey`, `Environment`, `ManagementAuth`) need a management key, sent as `Authorization: Bearer KEY_ID:SECRET`. The client sends one credential, so use a second client for management calls:

```ts
const mgmt = new HoneycombSDK({
  apikey: process.env.HONEYCOMB_MANAGEMENT_KEY,
  auth: { name: 'Authorization', prefix: 'Bearer' },
})
```

For the EU region, pass `base: 'https://api.eu1.honeycomb.io'`.

**Model corrections.** The first generation pass read Honeycomb's dataset-scoped paths, such as `/1/slos/{datasetSlug}`, as "load one record by id", so the list operations were missing. The corrections are in `.sdk/model/guide/guide.aontu` and survive regeneration:

- `list({ dataset_slug })` and `load({ dataset_slug, id })` for SLOs, triggers, markers, marker settings, burn alerts, query annotations, columns and calculated fields.
- JSON:API envelopes (`body.data`) unwrapped for the `/2/` endpoints.
- `/1/kinesis_events` is `KinesisEvent`, not `Kinesi`.
- Deleting a board view is `BoardView().remove()`, not `Board().remove()`.
- `/2/auth` is a separate `ManagementAuth` entity, so it no longer collides with `/1/auth`.

**Live check and report.** `examples/smoke.mjs` runs the TypeScript SDK against api.honeycomb.io (pass `--dry` to print the requests without sending them). Findings from building this SDK, with suggestions for the generator, are in [DX-REPORT.md](DX-REPORT.md).

## Entities, not endpoints

This SDK exposes the API as **28 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `remove`):

```ts
const client = new HoneycombSDK()
const items = await client.ApiKey().list({ team_slug: "example" })
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Offline unit testing

Every SDK ships a built-in **test mode** that swaps the HTTP transport for
an in-memory mock, so your unit tests run fully offline — no server, no
network, and no credentials:

### TypeScript

```ts
// The offline mock starts EMPTY — seed it with the records the test needs.
// Shape: { entity: { <entity-name>: { <id>: <record> } } }
const client = HoneycombSDK.test({
  entity: {
    dataset: {
      test01: { id: 'test01', name: 'example_name' },
    },
  },
})
const datasets = await client.Dataset().list()
// datasets is an array of Dataset entities, one per mock record
console.log(datasets.map((dataset) => dataset.data()))
```

### Python

```python
client = HoneycombSDK.test()
datasets = client.Dataset().list()
print([item.data_get() for item in datasets])
```

### Golang

```go
client := sdk.Test()
result, err := client.Dataset(nil).List(
    nil, nil,
)
```

## Quickstart

### TypeScript

```ts
import { HoneycombSDK } from '@waqar2403/honeycomb-sdk'

const client = new HoneycombSDK({
  apikey: process.env.HONEYCOMB_APIKEY,
})

// List all apikeys (returns ApiKeyEntity[], one entity per record)
const apikeys = await client.ApiKey().list({ team_slug: "example" })
for (const apikey of apikeys) {
  console.log(apikey.data())
}

// Load a specific boardview (returns the entity, a BoardViewEntity)
const boardview = await client.BoardView().load({
  board_id: 'example_board_id',
  id: 'example_id',
})
console.log(boardview.data())
```

The client sends the API key in the `X-Honeycomb-Team` header.

## Use it from an AI agent (MCP)

The generated MCP server exposes this SDK's list and load operations as
[MCP](https://modelcontextprotocol.io) tools that Claude, Cursor or Cline
can call directly. It only reads: create, update, patch and remove become tools when the SDK's model sets
`main: kit: target: 'go-mcp': tool: write: true`. Build and register it:

```bash
cd go-mcp && go build -o honeycomb-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "honeycomb": {
      "command": "/abs/path/to/honeycomb-mcp"
    }
  }
}
```

## Quickstart in other languages

### Python

```python
import os
from honeycomb_sdk import HoneycombSDK

client = HoneycombSDK({
    "apikey": os.environ.get("HONEYCOMB_APIKEY"),
})

# List all apikeys (a list of entities, one per record; raises on error)
apikeys = client.ApiKey().list({"team_slug": "example"})
for apikey in apikeys:
    print(apikey.data_get())

# Load a specific apikey (returns the entity, raises on error)
apikey = client.ApiKey().load({"id": "example_id", "team_slug": "example_team_slug"})
print(apikey.data_get())
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## How-to guides

### Make a direct API call

When the entity interface does not cover an endpoint, use `direct`:

**TypeScript:**
```ts
const result = await client.direct({
  path: '/api/resource/{id}',
  method: 'GET',
  params: { id: 'example' },
})
if (result.ok) {
  console.log(result.data)
}
```

**Python:**
```python
result = client.direct({
    "path": "/api/resource/{id}",
    "method": "GET",
    "params": {"id": "example"},
})
```

**Go:**
```go
result, err := client.Direct(map[string]any{
    "path":   "/api/resource/{id}",
    "method": "GET",
    "params": map[string]any{"id": "example"},
})
if err != nil {
    panic(err)
}
fmt.Println(result)
```

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

## Customizing this SDK

This repository contains its own generator (`.sdk/`), so the SDK is
customizable without forking any upstream tool:

- **The model** (`.sdk/model/`) declares everything this project owns:
  package names, versions, active features, per-target settings. It is
  written in [aontu](https://aontu.dev), a JSON-based
  specification language designed for building ontologies: easy to edit
  by hand, and files unify rather than override, so small declarations
  compose into one model. Regeneration re-reads it every time.
- **Templates** (`.sdk/tm/`) and **components** (`.sdk/src/cmp/`) are
  the two layers of generation, copied into this repo: templates are the
  literal per-language source, components generate the API-shaped parts.
- **Regeneration overwrites.** Each run rewrites every generated file from
  the model, the templates and the components, so an edit made to
  generated output is lost. Say what this project needs in its own model
  (`.sdk/model/sdk.aontu`), or extend a target with a component of its
  own in `.sdk/src/cmp/<target>/`, registered with `registerComponent`,
  which `voxgig-sdkgen doctor` reports as an addition rather than drift.
- **Custom features and entire custom targets** arrive through sdkgen
  packages (`voxgig-sdkgen package add`), on the same rails as the
  bundled languages, and `voxgig-sdkgen doctor` reports any drift from
  what a resync would write.

How-to: [customize and propagate templates](https://github.com/voxgig/sdkgen/blob/main/docs/how-to/customize-and-propagate-templates.md).
The full story: [voxgig.com/sdk/custom](https://voxgig.com/sdk/custom).
